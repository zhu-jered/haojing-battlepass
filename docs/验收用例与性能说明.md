## 2. 性能说明（§13）

### 2.1 硬指标与实现依据

| §13 要求 | 实现方式 | 代码位置 |
|---|---|---|
| 轮询类检测统一每 20 tick 一次 | 所有周期性检测都挂在**同一个**每秒维护处理器上，进入即按 20 tick 节流 | `HaoJingBattlePassServer#onInitialize` + `runMaintenance` |
| 禁止每 tick 遍历"全部玩家 × 全部任务" | ①任务按**动作建索引**，事件到达只比较同动作的少数任务；②彩蛋按**触发时机矩阵**筛选，只判定该时机相关的彩蛋 | `TaskProgressTracker#indexCache`、`EggService#TRIGGER_MATRIX` |
| 任务匹配按方块/实体/群系建索引 | 同上（索引在任务分配变化时失效重建，不在判定路径里做 IO） | `TaskProgressTracker#buildIndex` |
| 目标：30 人在线 TPS ≥ 19.5，且可测量 | 自增计数器 + 定期日志：写盘次数、同步修订号、握手统计、长夜状态定时日志 | `PlayerDataManager#writeCount`、`PlayerSyncService#revisionsOf`、`HandshakeService#describe`、`LongNightManager` 状态日志 |

### 2.2 每秒到底做了什么（30 人时）

| 工作 | 频率 | 30 人量级 |
|---|---|---|
| 配置文件变更检测（8 份） | 每秒 8 次 `lastModifiedTime` 查询 | 8 次系统调用 |
| 任务刷新判定 | 每秒 1 次日期比较；需要刷新时才动作 | 通常 0 成本 |
| 随机事件推进 | 每秒 1 次：冷却比较；到点才掷骰 | 0~1 次随机数 |
| 里程碑判定 | 每秒 1 次：10 条阈值比较 + 分母（**缓存 5 分钟**） | 10 次 long 比较 |
| 玩家状态同步 | 每秒 1 次：仅对**打开界面的玩家**重建快照；内容未变不发包 | 打开界面的人 × 5 个通道重建 |
| 长夜在线人秒计数 | 长夜中每秒加一次在线人数 | 1 次加法 |
| 赛季滚动核对 | 每秒 1 次字符串比较（快速路径） | 1 次比较 |

**关键设计**：脏标记 + **内容比较**。即使每秒都尝试重建，只要 JSON 与上次发送的一致就**不发包、不计修订号**，
因此网络流量与实际数据变化量成正比，而不是与玩家数量成正比。

### 2.3 网络流量估算

一次同步快照的实际大小（实测 JSON 文本）：

| 通道 | 典型大小 | 触发时机 |
|---|---|---|
| `player` | ~0.3 KB | 界面打开时每秒检查（内容变化才发） |
| `tasks` | 1.5~3 KB | 任务进度变化 / 打开界面 / 每 2 秒兜底检查 |
| `shop` | ~1 KB | 打开界面、购买后 |
| `titles` | ~0.3 KB | 佩戴、解锁称号后 |
| `collection` | ~0.3 KB | 解锁彩蛋、达成里程碑后 |
| `admin` | ~1 KB | 只有 OP 打开面板时 |

单包上限 32 KB（`PacketCodecs.byteArray(32768)`），分片上限 16 KB × 64 片 = 1 MB，
**超过上限的分片包直接丢弃并记日志**（§14）。正常快照永远只用 1 片。

### 2.4 已知的性能边界（诚实列出）

| 项 | 现状 | 何时需要优化 |
|---|---|---|
| 静听彩蛋按**每 tick** 采样 | 只对"长夜中 + 静听未解锁"的玩家做一次浮点比较（§6 明确要求每 tick，见 D-23） | 长夜在线人数很大（几百人）时，可改成每 5 tick 采样并在判定时按 `deltaTicks` 折算（判定器已支持） |
| 里程碑"全服"口径的发放 | 达成瞬间遍历所有玩家存档并逐个发奖（含离线） | 玩家数达数百时改成后台线程发放 |
| 人均口径的分母 | 缓存 5 分钟，刷新时遍历一次玩家目录 | 需要即时性时改成在 JOIN/QUIT 时维护计数 |
| 玩家进度写盘 | 标脏 + **5 秒**节流合并，后台线程写 | 已是 §12 要求的形态；若要更细可调 `PlayerDataManager` 的间隔 |
| 里程碑计数落盘 | 内存累加 + **60 秒**合并；达成瞬间立刻落盘 | 若不能容忍丢失 1 分钟计数，可把间隔调小（代价是更多 IO） |
| 排行榜定时重建 | `RankingService` 每 60 秒遍历"磁盘存档 ∪ 内存缓存"全部玩家聚合排序，结果缓存只读快照，不在打开界面时现算 | 几百人规模可接受；上千人时改成后台分批扫描增量聚合 |
| 赛季结算发放 | 仅在赛季轮换瞬间遍历旧赛季玩家逐个按等级档位发奖（一月一次低频动作），与里程碑全服发放同一口径；单条/单玩家异常被捕获不阻断轮换 | 几百人规模可接受；上千人时改成后台分批结算，避免轮换瞬间一次性遍历全服存档 |

### 2.5 怎么量（给运维的测量方法）

1. 服务端日志每秒一行的长夜状态里带时间戳与在线人数 —— 直接看有没有规律性的卡顿间隔。
2. `/tps`（原版指令）与 `debug` 报告配合；压测时建议先 `/forge tps` 之类的等价物或看 spark 报告（如果有）。
3. 模组自身的计数器：
   - 关服日志：`关服数据已全部落盘（赛季 N 份 / 永久 N 份 / 累计写入 N 次）` —— 写入次数应与玩家行为量级相符，而不是每秒飙升。
   - 客户端日志（debug 级）：`已同步通道 X 给玩家 Y（修订 N，字节数，片数）` —— 只有真的变化时才出现。
4. 回归基线：`gradlew test` 的 389 个测试全绿（其中包含限流、幂等、分片重组、签到并发、排行排序、赛季任务归属、结算档位匹配、轮换幂等与重置后任务即时补齐这些与"卡服/刷包/重复发奖/清档后空任务"直接相关的用例）。
