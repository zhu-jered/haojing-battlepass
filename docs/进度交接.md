> **始终用 `--no-daemon`**（daemon 在本机常卡死）。
> **JDK 21 必须显式指定**：本机 PATH 上的 `java` 当前是 11（`C:\Program Files\Java\jdk-11.0.32.101-hotspot`），
> 不设 `JAVA_HOME` 时 Gradle 直接报 "Gradle requires JVM 17 or later"。JDK 17 / JDK 21 都装在
> `C:\Program Files\Java\`，本模组编译目标是 21，用 `jdk-21.0.12.1`。

**历史坑（若将来目录又含中文，会重新遇到）**：

| 坑 | 现象 | 处理 |
|---|---|---|
| 工程目录含中文 | Gradle 测试 worker 报 `ClassNotFoundException: GradleWorkerMain` | Gradle 固定用 Java `@argfile` 传 worker 类路径，而 JDK 用系统 ANSI 代码页（GBK）解析 argfile，**处理不了非 ASCII 路径**，且 `-Dfile.encoding` 无效。保持目录纯 ASCII |
| **`GRADLE_USER_HOME` 含中文** | **同样报 `GradleWorkerMain` 找不到** | 必须用 ASCII 路径引用 |
| 从中文目录构建 | 测试被**跳过** | `server/build.gradle` 在路径含非 ASCII 时跳过测试并打印三条提示 |
| 在 DSH 里跑 Gradle **打包** | `:server:remapJar` 失败：`the jar file ... can't be written` | 沙箱 workspace-write 下 `Files.isWritable()` 对**所有路径**恒为 false → JDK zipfs 判为只读。**编译与测试不受影响**；打包需要提权或自己在普通终端跑 |

**版本锁定**（`gradle.properties` 是唯一来源）：MC `1.21.11` / Loader `0.18.1` / Fabric API `0.140.2+1.21.11` / Loom `1.14.6` / Yarn `1.21.11+build.6` / Gradle `9.2.0` / JDK 21。

**镜像**：本机 hosts 把 `*.mojang.com`、`libraries.minecraft.net`、`github.com` 全系指向 127.0.0.1。
绕法用的是 Loom 官方钩子，没有一处臆造（细节见 `gradle.properties`、`settings.gradle`、根 `build.gradle` 的中文注释，以及偏差档 D-7）：

| 需要的东西 | 绕法 |
|---|---|
| Gradle 发行版 | wrapper 的 `distributionUrl` 指腾讯镜像 |
| 版本清单 / 客户端·服务端 jar | `loom { customMinecraftMetadata }` 指 BMCLAPI + 在 settings 阶段把 jar 预置进 Loom 缓存（**sha1 校验**） |
| 原版库仓库 | `loom_libraries_base` 指向**本机自建 Maven 仓库**（`GRADLE_USER_HOME/local-maven`），因为 Maven Central 完全没有 `com.mojang:*` 这批构件，而 BMCLAPI 会 302 到短时效志愿者节点 |
| assets（仅 runClient 用） | `loom_resources_base` 指 BMCLAPI，**尚未实测** |

首次运行会自动预热物料（下载 + 校验），已就绪时零开销。删掉 `.gradle-home/` 不会坏，只会重新预热。

## 2. 已完成阶段

### 阶段 1 — 骨架与构建配置
三子工程 `:common` / `:server` / `:client`。`:common` **不产出 jar**，它的源码由两个成品工程用 `sourceSets...srcDir` 并入编译 —— 这样只交付两个 jar、两份 `fabric.mod.json`，且两端协议类由同一份源码生成，从机制上杜绝分叉。

### 阶段 1B — 镜像打通 + 冒烟构建
`./gradlew build` 通过，产出 `haojing-battlepass-server.jar` / `-client.jar`。

### 阶段 2 — 数据层
- `JsonStore`：原子写（临时文件 + **fsync** + rename）+ 保留上一份 `.bak` + 损坏自动回滚 + 单玩家失败不影响他人。
- `PlayerDataManager`：`ConcurrentHashMap` 内存态 + 脏标记 + **5 秒节流异步落盘**（禁止主线程同步 IO）+ 退服后"落盘成功才释放内存"。
- 赛季数据与永久数据**分成两个文件**，赛季重置只需删赛季文件，永久数据（星币/收藏册）连碰都不用碰。

### 阶段 3 — 时间工具 + 配置层 + 长夜模式
- `TimeUtil`：全局固定 `Asia/Shanghai`（tzdata 坏时退固定 +08:00，**不退系统时区**）；跨零点时段；§5.2 的**业务日边界**（以 `dailyRefreshTime` 切分）。
- `ConfigManager`：首次运行落地 `season.json`；非法值**只修正 + 告警，不拒绝启动**；损坏从 `.bak` 回滚；`reloadIfChanged()` 让"改配置不重启即生效"（§16 验收项）。
- 长夜：`LongNightSchedule`（纯排程逻辑）+ `LongNightManager`（开始前 10 分预告 / 开始全服标题 / 结束前 10 分预告 / 定时状态日志）+ `LongNightEffects`（原版 `SLOWNESS` + `MINING_FATIGUE`，**短时长+周期刷新**，因此白名单与长夜结束都会 5 秒内自然失效，无需移除逻辑）。

### 阶段 4 — 任务系统（本工程最大的一块）
- **过滤器**（§5.7）：6 个条件维度（方块/实体/群系/维度/Y 区间/时段）+ AND/OR 任意嵌套。失败方向一律取"不命中"。
- **任务池**：内置 **42 条**默认任务（12 探险 + 12 建造 + 12 综合 + 6 每周），首次运行落地成 `daily_tasks.json`；加载时**递归校验**，非法任务**丢弃 + 告警**（绝不猜 `action`、绝不让坏过滤器静默失效）。
- **抽取**：每日三组各 1，同日不重复 + 与昨日不重复；每周 3 个（按周一对齐的周键，§5.4）。重 roll 换任务并**作废旧进度**，次数受 `dailyRerollLimit` 限制。
- **防刷**（§5.8）：只统计玩家本人（事件语义天然保证）、假人按 `bot_` 前缀排除、CLAIMED 后不再计数、**同玩家+同动作+同坐标**在同 tick 只计一次。
- **刷新**（§5.3）：在线玩家在主线程改内存（然后异步落盘），离线玩家交给后台线程做 IO；全局幂等标记 `lastDailyRefreshDate` **最后才写**（崩溃最坏是重刷一次，而不是漏刷）。
- **事件**：破坏/击杀用 Fabric 现成事件；**放置/钓鱼/交易 3 处 Mixin**；群系/维度/坐标每 20 tick 轮询（按"条件由假变真"计数）。

### 阶段 5 — 战令等级 / 分支 / 星币 / 商店 / 每日经验上限 / 赛季滚动
- **经验与升级**：`LevelCurve`（曲线 `50 + 10×(级-1)`，可配置，**文档未给数值**，见 D-14）+
  `BattlePassService#addXp`。顺序固定为「先乘长夜倍率（§5.11，按玩家，白名单豁免）→ 再受每日上限截断（§5.10）」，
  倍率取整用四舍五入；满级后返回"满级"而不是把经验塞进经验条。
  每升 1 级 +10 星币（§4），写在**永久数据**文件里。
- **每日经验上限**（§5.10）：`dailyXpCap` 默认 500，可部分发放（上限内的照发）；
  `0` 表示不限（`remainingDailyXp` 返回 -1）。任务进度照常累计 —— 这一点是任务系统本来就有的行为，
  经验发放是领取时才发生的。
- **分支**（§4）：`chooseBranch` 校验等级门槛与"本赛季锁定"；`adminSetBranch` 供管理员改选。
  两者都会**补发已达等级的分支奖励**（去重键带分支名，不会重复发）。
- **奖励统一抽象**（§9）：`Reward` / `RewardType`（含新增的 `EXEMPT_CARD`，见 D-13）+
  `RewardSink` 接口。实现分两层：`DataRewardApplier`（星币/称号/豁免卡/战令经验，**离线也能发**）
  与 `MinecraftRewardSink`（ITEM/COMMAND，需要在线玩家；命令走 `CommandWhitelist` 白名单）。
  这样 `BattlePassService`、`ShopManager` 完全不引用 Minecraft 类型，规则全部可单元测试。
- **等级奖励表**：`config/haojing_battlepass/rewards.json`（1~30 级 + 双分支），
  默认内容随 jar 分发、首次运行落地、热重载；升级时自动发放 + 进服/改分支/热重载后补结算。
- **商店**：`config/haojing_battlepass/shop.json` + `ShopManager`。扣款与限购检查在同一把锁内完成；
  **发放失败会原路退款**（收钱不给货不可接受）；限购次数记在永久数据（D-18）。
- **任务领奖与豁免卡**（§5.5/§5.9）：`claimTaskReward` 用"状态机单向迁移"保证幂等
  （检查+置位在同一把锁内，重复点击只会得到 `ALREADY_CLAIMED`）；
  `useExemptCard` 把每日任务组直接置为 CLAIMED（**不发奖**），拒绝用在"已完成待领取"的任务上（D-17）。
- **赛季归档与重置**（§4、§12）：`SeasonResetService`。判据是"玩家存档的 seasonId ≠ 配置的 seasonId"
  （见 D-16）；在线玩家在主线程改内存、离线玩家交给后台线程改文件（与每日刷新同一套分法）；
  归档写 `data/history/season_<id>.json`（同赛季多次写入会**合并去重**）；
  重置后**保留星币与收藏册**（由存储结构保证：它们根本不在赛季文件里）；
  结算公告走"待播报"标记，等有玩家在线时才播。
- **接线**：`HaoJingBattlePassServer` 新增每秒维护 `runMaintenance`（任务池/奖励表/商店的热重载 +
  任务刷新 + 赛季滚动 + 补播公告），全部集中在 20 tick 节流里。

### 阶段 6 — 彩蛋 / 随机事件 / 节日口令 / 全服里程碑
- **彩蛋系统**（§6）：`EggEvaluator` 把 13 条量化判定逐条实现（长安拂晓 / 月下筑者 / 鱼信 /
  大地勘探者 / 社团同游 / 樱落归镐 / 守夜人 / 长夜微光 / 晨归 / 静听 + 三条轻量趣味彩蛋），
  `EggService` 负责一次性解锁（写永久收藏册）、赛季限定语义（进度随赛季重置、成就永久保留）、
  长夜专属**零经验**（配置写了也会被修正）。**判定器与业务全部 MC-free**，
  跨零点、分离 10 秒重置、跨长夜窗口归零、每 tick 位移阈值这些边界都有单测。
- **Minecraft 侧接入**（`EggEvents`）：每 20 tick 完整快照（位置/群系/月相/天气/户外/同伴/敌对/装备/手持）
  + **每 tick 只对"长夜中且静听未解锁"的玩家**做位移采样（§6 明确要求每 tick，见 D-23）
  + 事件驱动（放置、钓鱼、群系进入、树苗长成、长夜窗口结束、死亡、聊天）。
- **随机事件**（§10）：`RandomEventService`（纯调度：概率、最小间隔 90 分钟、时长、参与判定、
  参与者发奖、事件期间经验倍率）+ `RandomEventEffects`（状态效果 / 刷怪 / 物品 / 白名单命令）。
  **长夜期间照常运行**，其经验奖励同样受 §5.11 减半与 §5.10 上限约束（倍率在入口处相乘）。
- **节日口令**（§10）：`RedeemCodeService`（忽略大小写与首尾空白、MM-dd 生效时间段含跨年、
  每人每口令一次且在玩家数据的锁内原子占位）+ 聊天监听 `RedeemCodeEvents`。
- **全服里程碑**（§10、§13）：`MilestoneService` 的自增计数器 + 9 个指标 + 两种口径（全服累计 / 人均）
  + 两种发放对象（全服 / 参与者）；计数在内存累加、**每 60 秒合并落盘**，达成瞬间立刻落盘且只发一次。
- **轻量趣味彩蛋**（§6）：聊天关键词广播（带冷却）、生日祝贺、节日问候（MM-dd 窗口，含跨年）。

### 2.5.8 怪物潮亮度闸修复（2026-10-22，本次接手）

**玩家反馈**：怪物潮随机事件无视亮度直接在玩家身边刷怪，白天室内、火把照亮的基地与生电机房都会刷出怪物，导致机器被破坏。

**根因**：`RandomEventEffects.applySpawn` 旧实现直接在玩家脚下 ±8 格随机偏移刷怪，**不看亮度、不找地面**，脚位直接取玩家 Y（可能埋进方块或悬空）。

**修复内容**：
- `RandomEventConfig` 新增四个全局刷怪策略（`events.json` 顶层，热重载，校验夹紧到安全区间）：
  `spawnMaxLightLevel`（默认 7，0~15）、`spawnRadius`（默认 8，1~32 格）、`spawnMaxAttempts`（默认 12，1~32）、
  `spawnVerticalRange`（默认 10，1~32 格）；配套 `effectiveSpawn*()` 访问器绕过校验也夹紧。
- `RandomEventEffects` 构造函数新增 `Supplier<RandomEventConfig>`（装配在 `HaoJingBattlePassServer` 638 行，
  传 `events::config`）；`applySpawn` 改为每只怪先调 `findSpawnSpot` 找合法暗点，找不到就**放弃这一只**，
  绝不硬刷到亮处，日志记录跳过数量。
- `findSpawnSpot`：随机取列（离玩家水平两格内换点），在垂直窗口内自上而下找第一处
  "脚下实心 + 脚位空气 + 头顶空气"，再复核 `getLightLevel(feet) ≤ 阈值`；任一不满足换下一列。
- 内置 `default_events.json` 写入四个默认值；管理员手册 events.json 行已补字段说明；偏差档 D-31 记录取舍。
- 新增 `RandomEventConfigTest`（5 个用例：默认值、亮度夹紧、半径/尝试次数夹紧、垂直高差夹紧、
  绕过校验的有效访问器夹紧）。**310 测试全绿**。

**关键代码定位**：
- `server/.../event/RandomEventConfig.java`：策略字段 + `validate()` 夹紧 + `effectiveSpawn*()`
- `server/.../event/RandomEventEffects.java`：`applySpawn` / `findSpawnSpot`
- `server/.../HaoJingBattlePassServer.java`：638 行构造注入 `events::config`
- `server/src/main/resources/haojing_battlepass/default_events.json`：四个默认策略值

**已知边界**：
- 亮度闸对所有 `SPAWN` 效果统一生效；要做白天友好实体事件，把 `spawnMaxLightLevel` 调到 15 即关闭闸。
- 亮度取世界综合亮度（方块光 + 天空光），与原版敌对怪生成判定同源。
- 选点逻辑尚未真机验证（单测只覆盖参数夹紧；真实世界的地面/亮度判定需进服实测）。

### 2.5.9 随机事件自查修复 + 新增默认事件（2026-10-22，本次接手）

**触发**：用户要求"自查 bug，随机事件自行新增内容，全部自主决策"。通读事件四层代码（配置 / 调度 / 效果 / 定义）后修复 4 处问题、新增 4 个默认事件。

**修复**：
1. **权重溢出可致事件系统崩溃（最重要）**：`pickWeighted` 用 `int total` 累加权重，而 `validate()` 只夹下限不夹上限——两条 2^31 级权重相加溢出为负，`random.nextInt(负数)` 抛异常。修：`validate()` 把 `weight` 夹紧到 1~100 并 WARN；`pickWeighted` 改用 `long` 累计 + `random.nextLong(total)`（双保险，不依赖校验）。
2. **已参与玩家动作仍无谓累加**：`onAction` 未检查 `participants`，达标后每次动作仍 merge 递增，大 target 事件下计数无界增长。修：已参与直接返回。
3. **同一物品可能重复发放**：同一事件"奖励表 ITEM"与"效果表 ITEM"并存时玩家各拿一份，配置层无提示。修：`validate()` 检测并存并 WARN（不拦截，保留"有意双份"的活动空间）。
4. **`RandomEventEffects` 死参数**：`applyStart/applySpawn` 的 `List<UUID> online` 从未使用（实际遍历全服在线玩家）。修：删除死参数并注释说明"事件是全服事件，与参与判定无关"；调用点 `HaoJingBattlePassServer` announcer 同步去掉该参数。

**新增 4 个默认事件**（`default_events.json`，类型枚举各新增一项，客户端 `zh_cn.json` 补公告文案）：
`ev_pillager_raid`（掠夺者入侵，KILL_ENTITY×2，刷掠夺者×3+卫道士×1，奖励经验 90+京币 8+绿宝石×4）、
`ev_harvest_festival`（丰收庆典，BREAK_BLOCK×5，急迫+幸运 8 分钟，经验 40+京币 3）、
`ev_fishing_derby`（钓鱼大赛，FISH×2，幸运 II 10 分钟，经验 35+京币 2）、
`ev_mining_rush`（挖矿热潮，BREAK_BLOCK×4，急迫 II 8 分钟，经验 45+京币 5）。
全部复用既有 5 种效果与 6 种参与口径，不新增效果/参与类型；掠夺者入侵的 SPAWN 同样走亮度闸。

**关键代码定位**：
- `server/.../event/RandomEventConfig.java`：weight 夹紧 1~100 + `warnOnDoubleItemReward()`
- `server/.../event/RandomEventService.java`：`onAction` 提前返回 + `pickWeighted` long 累计

### 2.5.11 自然月周期 + 到期自动轮换（2026-10-22，用户拍板每月 1 号一个赛季）

① 系统自动滚动（到期自动归档、重置、公告，无需管理员改 `seasonId`）；② 自然月（每月 1 号切换，
28/30/31 天跟随日历，不固定 30 天）。

**新增内容**：

| 项 | 说明 | 文件 |
|---|---|---|
| `cycleMode` | `"natural"` 自然月 / `"fixed"` 固定时长（历史兼容）；非法取值校验归一化为 `fixed` 并 WARN；Java 默认 `fixed`，旧存档/旧配置行为不变 | `SeasonConfig` / `ConfigManager.validate` |

**关键边界（必须保持一致）**：
- 自动轮换**只清档与轮换赛季 ID**；任务池、奖励表、主题名 `themeName` 仍由管理员手动更换。

**关键代码定位**：

**约定（后续请沿用）**：
1. 每个文件顶部写**用途**；注释解释**为什么**，不只解释"是什么"。
2. JSON 载体（DTO / 配置）用 **public 字段 + Gson**；行为逻辑放服务端业务类，不让 DTO 变胖。
3. 所有枚举都配一个**宽容的 `fromName`**：Gson 遇到未知枚举值会抛异常，会被持久化层当成"文件损坏"而回滚，造成数据丢失。
4. 数据模型放 `:common`（两端契约），业务与持久化放 `:server`。
5. 写盘一律走 `JsonStore`；热重载一律用 `FileChangeDetector`（它封装了"自己回写不能被当成外部改动"这个坑）。
6. 轮询类检测统一**每 20 tick 一次**（§13 性能预算）；匹配按动作/方块/实体/群系**建索引**，禁止遍历"全部玩家 × 全部任务"。
7. 文案走 **TranslationKey**，译文放客户端 `zh_cn.json`（§1 要求）。
8. **不确定的 API 一律先核实**，不要凭印象写：`javap` 查签名、或读反编译源码。反编译源码已生成，见下。
9. **需要单元测试的业务类不要引用 Minecraft 类型**（Loom 不把 minecraft 挂到测试源集，
   引用了一加载就 `NoClassDefFoundError`）。做法是先例：`TaskProgressTracker`（纯判定）、
   `BattlePassService`（倍率走 `XpMultiplierProvider`、发奖走 `RewardSink`）、
   `SeasonResetService`（公告走 `Announcer`）、`ShopManager`（发放走 `RewardSink`）。
10. **配置类管理器统一三段式**（先例：`TaskPoolManager` / `LevelRewardManager` / `ShopManager`）：
    首次运行从 jar 内置资源落地默认文件 → 加载后校验 + 回写一次 + `changeDetector.reset` →
    `reloadIfChanged()` 热重载；非法条目**丢弃 + 逐条 WARN**，绝不拒绝加载整份配置。

| 三个 Mixin 的注入签名已逐项核对 | `ServerPlayerInteractionManager#interactBlock`、`FishingBobberEntity#use`、`TradeOutputSlot#onTakeItem`（含 `Merchant#trade(TradeOffer)` 的描述符）都在 1.21.11 上与 Mixin 代码完全一致，**不会因为签名不匹配而崩** |
| **从未启动过 `runServer` / `runClient`** | 全部验证止于"编译 + 打包 + 297 个单测"。因此下面这些**只保证编译与逻辑正确，未在真机跑过**：`RandomEventEffects`（刷怪/药水/命令）、`EggEvents`（月相/天空可见/同伴统计/树苗生长）、`ChatTitleDecorator`（聊天前缀）、三个界面（布局与按钮位置）、握手与同步链路（真机两端的实际交互） |
| 界面未做视觉验证 | 三个界面已改为**按屏幕尺寸自适应**（`common/gui/PanelLayout`，有 9 条布局断言兜底：不越界、页签折行、按钮落在面板内），但**仍未截图看过实际渲染效果**。第一次进游戏时重点看：中文是否越界、行文字与按钮是否重叠、九个管理页签在窄屏下的折行是否美观 |
| 配置阶段拿不到玩家 UUID | 1.21.11 的 `ServerConfigurationNetworkHandler#getProfile()` 是 protected（见 D-26/D-27），因此"握过手"无法绑定到玩家身份；客户端校验靠三处能力校验。这不是安全问题（§2 明确不是反作弊） |
| 管理面板只直接编辑数值型参数 | 内容型清单（任务/奖励/商店/彩蛋/口令/事件/里程碑）通过"改文件 + 1 秒热重载 + 导出/导入"维护（见 D-28） |
| 里程碑"全服"口径会在达成瞬间同步发奖 | 发放对象是 ALL 时，那一刻会遍历所有玩家存档并逐个发奖（含离线）。30 人服没问题，几百人时需要改成后台发放，否则会卡一下 |
| 人均口径的分母缓存 5 分钟 | 新玩家加入后分母最迟 5 分钟后才更新。里程碑是长期目标，影响可忽略；若要求即时，需要一个玩家计数缓存并在 JOIN 时递增 |
| 静听的每 tick 采样 | 只在"长夜中 + 静听未解锁"时对每个在线玩家做一次浮点比较（见 D-23）。若将来把 `stillSeconds` 调得很大且长夜在线人数很多，这里是唯一的每 tick 热点。判定器已支持按 `deltaTicks` 折算，改成 5 tick 采样即可降一个数量级 |
| 离线刷新的窄并发窗口 | 后台线程写离线玩家文件时该玩家恰好上线，可能读到刷新前内容 → 当天仍拿旧任务，次日自动纠正。刷新在 06:00 低峰，加锁不划算，已接受并写进注释 |
| 赛季滚动的同类窄窗口 | 与上一条同源：后台归档线程写某个离线玩家文件时该玩家恰好上线，两端会各改一份。同样被接受（赛季滚动是 30 天一次的运维动作，且判据是 seasonId 不一致，下一轮会重试） |
| 离线玩家拿不到物品/命令奖励 | 见 D-15。等级奖励的整组去重意味着"离线时错过的物品奖励"只有下一次上线补发一次的机会；商店则直接退款。**若将来需要"绝不错过"，需要一个待领物品队列** |
| 新玩家在赛季滚动后拿到的默认 seasonId | 已修：滚动完成时调 `PlayerDataManager#setSeasonId`。改动此处代码时别把这行删掉，否则新玩家的存档会带着旧赛季 ID，下次开服被当成旧档再重置一次 |
| `loom_resources_base` 仍未实测 | 只有 `runClient` 用到（拉原版 assets）；第一次 `runClient` 时验证 |
| `genSources` 不能从根工程跑 | 两个子工程共享 loom 缓存的合并 jar，Gradle 会因任务依赖校验失败报错；**单跑 `gradlew :server:genSources`** 即可 |
| 测试日志目录 | Minecraft 的库把 logback 带进测试类路径，测试工作目录是子工程目录 → 会在 `server/logs/` 写日志。已加入 `.gitignore` |
| Gradle `File watcher` 报 `error = 5` | 沙箱下 Gradle 的原生文件监视线程起不来，**只是 stderr 噪音**，不影响编译/测试/打包；对应命令的退出码可能是 1，判断成功与否要看 `BUILD SUCCESSFUL` |
