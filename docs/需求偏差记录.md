# 需求偏差记录

本文件记录**实现与《镐京方块协会战令 Mod 开发提示词（最终稿 v2）》不一致的地方**，以及不一致的原因。
凡与文档不符之处一律登记在此，避免后续阶段有人照着文档又改回去。

## D-1　拼音更正：gaojing → haojing

| 项 | 文档写法 | 实际实现 |
|---|---|---|
| 服务端 Mod ID | `gaojing_battlepass` | `haojing_battlepass_server` |
| 客户端 Mod ID | （未给，仅一个 ID） | `haojing_battlepass_client` |
| 包名 | `com.gaojing.battlepass` | `com.haojing.battlepass` |
| 配置/数据目录 | `config/gaojing_battlepass/` 等 | `config/haojing_battlepass/` 等 |
| 日志前缀 | `[GaoJingBP]` | `[HaoJingBP]` |

**原因**：「镐京」的「镐」是破读音，读 **hào**（镐京，西周都城），不读 gǎo。文档的 gaojing 是拼音笔误。
**决定**：用户确认全部更正为 haojing，且服务端/客户端两个 Mod 分别命名（Fabric 要求 Mod ID 唯一）。
**落地**：`ModConstants`、`gradle.properties`、两处 `fabric.mod.json`。

## D-2　放弃「刷怪倍率」与「全局实体数量上限」（文档 §7）

**文档要求**：长夜期间"怪物生成率倍率提升 + 全局实体数量上限（超限则拒绝生成，防 TPS 崩溃）"，
配置项为 `longNight.mobSpawnMultiplier` 与 `longNight.entityCap`（§18 样例中分别为 1.5 与 200）。

**实际实现**：**不实现**。配置项一并移除。

**原因（已查证，非推测）**：
1. Fabric API 0.140.2 **不存在任何"否决刷怪"的事件**。全部实体相关事件只有
   `ENTITY_LOAD` / `ENTITY_UNLOAD` / `ALLOW_DAMAGE` / `ALLOW_DEATH` / `EQUIPMENT_CHANGE`。
2. `ServerEntityEvents.ENTITY_LOAD` 的回调签名是 `void onLoad(Entity, ServerWorld)`，
   **返回 void，不具备取消能力**。
3. 文档 §5.6 给出的 Mixin 白名单**不包含**任何刷怪类，因此无法在不扩白名单的前提下"拒绝生成"。

**决定**：用户明确表示「不管刷怪的事情」，**直接放弃**该功能。
**注意**：因此本模组**没有**为防 TPS 崩溃提供实体上限保护。文档 §13 的"长夜实体上限生效"验收项**不适用**。

## D-3　放弃「苦力怕爆炸保护」（文档 §7）

**文档要求**：长夜期间"默认开启苦力怕爆炸取消（**事件内 cancel**，不炸建筑）"，
配置项为 `longNight.creeperGriefProtect`（§18 样例中为 true）。

**实际实现**：**不实现**。配置项一并移除。

**原因（已查证）**：Fabric API **完全不存在爆炸相关事件**——全库搜索 `explosion` 仅命中 4 处，

可选替代（Mixin 到爆炸逻辑，或长夜期间临时置 `mobGriefing=false`）均需扩大 §5.6 白名单或引入副作用。

**决定**：用户明确表示「直接放弃这个爆炸，不需要」。
**注意**：长夜期间苦力怕**仍会**破坏建筑。

## D-4　放弃「怪物增益（移速/伤害/血量/探测范围）」（文档 §7）

**文档要求**：长夜期间"怪物移速/伤害/血量增益与玩家探测范围扩大（**参数均可调**）"。

**实际实现**：**不实现**。相关配置项已从 `LongNightConfig` 移除。

## D-5　长夜疲劳强度取最小档（文档 §7 未给数值）

**文档要求**：§7「在线玩家获得【长夜疲劳】：直接使用原版 SLOWNESS + MINING_FATIGUE，可选叠加饥饿加速」。

**实现取值**（文档未给任何数值，故取最保守）：

| 参数 | 取值 | 说明 |
|---|---|---|
| `fatigueEnabled` | `true` | §7 明确要求生效，不是可选项 |
| `fatigueSlownessAmplifier` | `0`（I 级） | 文档无数值，取最小档 |
| `fatigueMiningFatigueAmplifier` | `0`（I 级） | 同上 |
| `fatigueHungerAcceleration` | `false` | §7 自己写作"可选" |

**实现要点**：状态效果按"短时长 + 周期性刷新"施加（每 20 tick 刷新一次、每次 5 秒），
因此长夜结束或玩家被加入白名单后，效果会在 **5 秒内自然消失**，无需任何移除逻辑，
也就不会误删玩家身上来自其他来源的同名效果。

## D-6　白名单管理员的经验减半豁免（对 §7 的明确化）

**文档写法**：§7 说管理员白名单"不受长夜**全部**效果影响"；§5.11 说长夜期间经验 ×0.5。
经验减半字面上是"战令联动规则"而不是施加在玩家身上的状态效果，因此存在解释空间。

**决定（用户确认）**：白名单管理员**连经验减半也豁免** ——
"管理员主要负责服务器管理事务，这些不需要对其产生影响"。

**实现**：经验倍率必须**按玩家**计算，不能用全局倍率。

```java
LongNightSchedule.resolveXpMultiplier(active, config, whitelisted)
// 长夜中：普通玩家 0.5，白名单管理员 1.0；非长夜：所有人 1.0
```

**对后续阶段的约束**：阶段 4/5 发放经验时**必须**传入玩家 UUID
（调用 `LongNightManager#xpMultiplier(UUID)`），不得缓存或复用某个全局倍率值。

## D-8　任务 schema 扩展：新增 `action` 字段（文档 §18 的样例无法表达 §5.6 的要求）

**问题**：§18 的任务样例只有 `filter` 字段，但过滤器里的 `BLOCK_ID` 只能表达"涉及某个方块"，
**无法区分「放置石头」与「破坏石头」**——两者的过滤条件完全相同。而 §5.6 明确要求
分别监听放置与破坏。也就是说，**按 §18 的样例写不出像"放置 64 个石头"这样的任务**。

**解决**：`TaskDefinition` 新增一个**必填**的 `action` 字段，取值：

| action | 挂载方式 |
|---|---|
| `BREAK_BLOCK` | Fabric 事件 `PlayerBlockBreakEvents.AFTER`（有现成事件，不写 Mixin） |
| `PLACE_BLOCK` | **Mixin** `ServerPlayerInteractionManager`（无现成事件，§5.6 白名单内） |
| `KILL_ENTITY` | Fabric 事件 `ServerEntityCombatEvents.AFTER_KILLED_OTHER_ENTITY`（有现成事件） |
| `FISH` | **Mixin** `FishingBobberEntity`（无现成事件，§5.6 白名单内） |
| `TRADE` | **Mixin** 村民交易处理（无现成事件，§5.6 白名单内） |
| `ENTER_BIOME` | 每 20 tick 轮询比对（§5.6 的规定做法） |
| `ENTER_DIMENSION` | 每 20 tick 轮询比对 |
| `REACH_POSITION` | 每 20 tick 轮询比对（§18 样例任务 `exp_001` 属于此类） |

**为什么要显式写出来而不是靠过滤器自动推断**：靠"过滤器里出现了 BLOCK_ID"无法判断是放置还是破坏，
猜错会把任务统计到完全错误的玩家行为上。因此无法识别的 `action` 会在配置校验阶段
**直接丢弃该任务并告警**，绝不猜。

## D-9　任务池 schema 扩展：每周挑战池与数量放进同一文件（文档 §18 只给了 `groups`）

**问题**：§18 的 `daily_tasks.json` 样例只有 `groups`（每日三组），没有规定每周挑战池放在哪里；
而 §5.4 要求每周挑战"数量默认 3 个"，§9 又要求管理员能增删改每周任务。

**解决**：在同一个文件里扩展两个字段：

```json
{
  "schemaVersion": 1,
  "weeklyCount": 3,
  "groups": { "explore": [...], "build": [...], "general": [...] },
  "weekly": [ ... 6 条 ... ]
}
```

**理由**：两类任务都是"任务池"，放在同一文件里管理员一处分清两类，
且刷新逻辑能共用同一套热重载与原子写；拆成两个文件只会多一份重复的加载/校验/热重载代码。

## D-11　新增全服状态文件 `data/haojing_battlepass/state.json`（文档 §12 未列此文件）

**问题**：§5.3 要求每日刷新时「写入全局标记 `lastDailyRefreshDate`」以保证幂等
（跨多天停服只补刷一次），但 §12 列出的目录只有"玩家数据"与"历史归档"，
没有地方放**全服**状态。这个标记不属于任何一个玩家，不能塞进 `players/<uuid>.json`。

**解决**：新增 `data/haojing_battlepass/state.json`，含 `schemaVersion`、
`lastDailyRefreshDate`、`lastWeeklyRefreshDate`。

**写入时机**：刷新流程的**最后**才写标记。若在刷新开始时写，中途崩溃会导致
"一部分玩家没被刷到却再也不会重试"；最后写的最坏情况只是重刷一次（当天任务被重抽），
是更安全的失败方向。

## D-12　Mixin 的实际使用范围与注入点（文档 §5.6 白名单内，但白名单措辞与实际类名有出入）

**实际只用了 3 处 Mixin**，全部落在 §5.6 白名单语义范围内：

| 行为 | 注入目标 | 判据（均读原版反编译源码确认，非猜测） |
|---|---|---|
| 放置方块 | `ServerPlayerInteractionManager#interactBlock`（HEAD + RETURN） | 目标位置方块**由 A 变为非空气的 B**，且手持物是 `BlockItem`（排除打火石/骨粉等非放置类右键） |
| 钓鱼成功 | `FishingBobberEntity#use(ItemStack)`（RETURN） | **返回值为 1**（读源码确认：钓上东西返回 1，勾到实体返回 3/5，空钩返回 0） |
| 村民交易 | `TradeOutputSlot#onTakeItem` 中对 `Merchant#trade(TradeOffer)` 的调用点 | 该调用只在材料确实被扣除后发生，等价于"一笔交易成交" |

**两处与 §5.6 措辞的实际出入（均按"更稳妥"处理）**：

1. **破坏方块与击杀实体不用 Mixin**。§5.6 把 `ServerPlayerInteractionManager`（破坏/放置）
   与 `Entity.kill`/`LivingEntity.damage` 列入白名单，但实测 Fabric API **已有现成事件**：
   `PlayerBlockBreakEvents.AFTER` 与 `ServerEntityCombatEvents.AFTER_KILLED_OTHER_ENTITY`。
   用事件比 Mixin 更稳（不受原版内部重构影响），也符合 §5.6「其余一律用 Fabric 事件」的精神。
2. **交易用 `TradeOutputSlot` 而不是 §5.6 提到的 `MerchantMerchantOffersS2CPacket`**。
   那个包是"服务端把交易列表同步给客户端"，在**打开界面**时就发，
   与"完成了一笔交易"完全是两回事。用它会把手贱点开界面也算成交易。
   §5.6 措辞里的"交易屏幕交互类"与本实现一致。

**由此带来的一个结论**：击杀的"只统计玩家本人"**不需要任何额外判断** ——
`AFTER_KILLED_OTHER_ENTITY` 给出的是"直接击杀者"，宠物/傀儡杀人时传进来的是那只狼本身、
不等于玩家，§5.8 天然成立。

## D-13　奖励类型扩展：新增 `EXEMPT_CARD`（文档 §9 的五类里没有）

| 项 | 文档写法 | 实际实现 |
|---|---|---|
| Reward 类型 | ITEM / COMMAND / BATTLEPASS_XP / STAR_COIN / TITLE | 上述五类 **+ EXEMPT_CARD** |

**问题**：§5.9 明确要求豁免卡「来源为战令等级奖励与商店兑换」。
也就是说等级奖励表（§9「1~30 级、双分支」）与商店商品都必须能表达"发一张豁免卡"，
但 §9 给出的奖励类型清单里没有这一类。

**若不扩展的后果**：只能把"哪一级发卡""商店哪件商品是卡"硬编码进代码，
管理员反而无法通过配置增删豁免卡的发放点，与 §9「全部热重载、可编辑」冲突。

**决定**：新增第六种奖励类型 `EXEMPT_CARD`。商店与等级奖励因此可以完全用配置表达。

## D-14　经验曲线数值由实现方拟定（文档通篇未给）

**文档要求**：§4 只规定「等级范围 1~30」，§18 的配置样例里也没有经验曲线；
§5.10 只给了每日经验上限 500。

**实际实现**：第 N 级升到 N+1 级需要 `xpPerLevelBase + xpPerLevelStep × (N-1)` 点经验，
默认 **base = 50、step = 10**，即 1→2 级 50 点、2→3 级 60 点……29→30 级 330 点，
**从 1 级练满 30 级共需 5510 点经验**（约合 110 个每日任务的产出）。

**为什么做成配置项而不是常量**：数值一定会被调整（§9 要求奖励管理可编辑），
把它放进 `season.json` 的 `xpPerLevelBase` / `xpPerLevelStep` 后，
管理员改配置即可（含热重载），不需要重新编译。校验规则见 `ConfigManager#validateLevelCurve`：
负数被夹紧为 0；两者同时为 0 会回退成默认曲线并告警（否则会出现"每级 0 经验"的死配置）。

**另一处取舍（文档未规定顺序）**：§5.10 的"每日已获得经验"统计的是
**长夜减半之后、真正进入经验条的经验**，而不是玩家行为的原始产出。
若不这样定，长夜期间玩家的实际每日上限会凭空翻倍。
实现顺序固定为「先乘 §5.11 倍率 → 再受 §5.10 上限截断」，并有单元测试锁住。

**取整规则**：倍率相乘后四舍五入（`Math.round`）。选四舍五入而不是向下取整，
是因为 0.5 倍下 1 点经验会被向下取整抹成 0，玩家会看到"进度涨了但经验一点没给"。

## D-15　离线玩家的物品/命令奖励无法发放（文档未规定）

**文档要求**：§9 允许奖励为 ITEM 与 COMMAND；§9 的数据维护部分允许管理员改任意玩家的等级。

**问题**：物品要塞进背包、命令要挂到玩家身上执行，**玩家离线时这两件事做不到**。
而"只改数据文件"的四类（星币/称号/豁免卡/战令经验）离线时完全可以发放。

**实际实现**（结构性区分，而不是各处 if 判断）：

| 奖励类型 | 离线玩家 | 行为 |
|---|---|---|
| STAR_COIN / TITLE / EXEMPT_CARD / BATTLEPASS_XP | 可发 | 正常发放，写入数据文件 |
| ITEM / COMMAND | 不可发 | 返回失败 + `WARN` 日志，**不**记为已发 |

**由此产生的一条重要行为**：商店在发放失败时会**原路退款**（`ShopManager#purchase`）。
商店与等级奖励的关键差别是"钱货"关系 —— 等级奖励是白送的，发失败最多漏发一次；
商店是玩家花星币买的，收钱不给货不可接受。

**等级奖励的权衡**：等级奖励按"级 + 分支"整组去重（先登记再发放），
因此离线时错过的物品奖励，会在该玩家**下次上线**时由 `grantDueLevelRewards` 尝试补发一次 ——
但如果那时仍然失败，这一组会被记为已发而不再重试。
选择这个方向是因为 §16 明确要求"同一奖励重复点击只发一次"，
重复发物品比漏发一次更难挽回。

## D-16　`state.json` 新增赛季字段，且赛季滚动的判据定为 `seasonId` 不一致（文档未给判据）

**文档要求**：§4 只说「赛季时长 30 天，管理员可改」，**没有规定赛季结束/滚动的判据**；
§12 给了 `data/history/season_<id>.json` 的归档位置，但没给全服赛季状态的存放位置。

**实际实现**：

1. **判据 = 玩家存档里的 `seasonId` 与配置里的 `seasonId` 不一致**。
   玩家存档从阶段 2 起就记录 `seasonId`（当时的注释已写明"阶段 5 处理"）。
   管理员推进赛季的动作就是把 `season.json` 的 `seasonId` 改成 `S2`；改完即热重载生效。

2. `data/haojing_battlepass/state.json`（D-11 新增的文件）再增两个字段：

## D-17　等级奖励的发放时机与豁免卡的使用限制（文档留白）

**等级奖励自动发放**：§9 要求管理员能编辑「1~30 级、双分支」的奖励，但没说玩家怎么拿到。
**实际实现**：升级时**自动发放**，并额外提供"补结算"路径（进服时、改分支时、奖励表热重载后）。

## D-22　全服里程碑的统计口径与默认条目（§10 要求"需定义"）

**实际实现**：

|---|---|
| 统计口径 | `TOTAL`（全服累计）与 `PER_CAPITA`（人均）两种，§10 明确要求都支持 |
| 指标枚举 | 9 个：破坏方块 / 放置方块 / 击杀生物 / 钓鱼成功 / 村民交易 / 领取任务 / 战令经验 / 长夜在线人秒 / 解锁彩蛋 |
| 默认条目 | 10 条（如"五万方块""万兽之敌""百万经验""百人时守夜"等），阈值与奖励均为可调默认值 |

| 人均口径的分母 | "协会玩家总数"（遍历玩家目录），**缓存 5 分钟** —— 里程碑是长期目标，分母的瞬时波动不影响判定，而每秒遍历目录是不可接受的 |

**为什么计数器不每次写盘**：破坏方块这类高频动作每发生一次写一次 JSON 会拖垮服务器。
内存 `ConcurrentHashMap` 累加，后台线程每 60 秒合并落盘一次，关服时同步再写一次；
**达成瞬间**会立刻落盘（因为奖励只发一次，重启后重算就会重复发）。
最坏情况（进程被杀）丢 1 分钟的计数。

## D-23　"静听"按每 tick 采样，与 §13 的"轮询统一 20 tick"冲突时的取舍

**文档矛盾**：§6 静听的判定写的是「长夜内**每 tick** 位移 < 0.01」，
而 §13 的性能预算要求「轮询类检测统一每 20 tick 一次」。

**决定（已用户确认）**：**以 §6 的量化定义为准**，保持每 tick 采样，但把开销压到最小 ——
只对"长夜中 + 静听彩蛋尚未解锁"的玩家做一次浮点减法与比较，
30 人同时在线的开销可以忽略。其余所有彩蛋一律走 20 tick 的完整采样。

**顺带说明"连续停留"的锚点语义**：§6 的社团同游要求"同群系连续停留 5 分钟"，
实现上第一次满足条件的采样只用来建立时间锚点（此时还不知道已经连续待了多久），
因此 5 分钟恰好需要 301 次 1 秒采样（t=1s 到 t=301s）。这是正确的保守方向 ——
宁可晚一秒触发，也不要提前触发。

## D-27　客户端校验能做到什么、做不到什么（§2）

**文档要求**："未握手的客户端拒绝进入 PLAY"。

**实际能做到的**（三处，见 `HandshakeService`）：
1. 配置阶段开始：客户端声明收不到握手结果通道 → 判定为原版/无 Mod 客户端 → **立即断开**；
2. 收到握手包：协议版本不一致 → 断开并回执"请更新 Mod"；
3. 进入 PLAY 时：再用 play 阶段通道做一次能力校验（防止只改配置阶段行为的客户端）。

**做不到的**：把"某个连接确实完成过握手"绑定到玩家身份上 ——
1.21.11 的配置阶段连接拿不到玩家 UUID（见 D-26），因此无法在 play 阶段复查"这个人握过手"。
**这不是安全问题**：§2 本身就说清楚了这个机制**不是反作弊**，只是避免玩家进服后面对空白界面；
所有业务判定仍然只在服务端，客户端提交的数据一律不作为判定依据。

  重置赛季（重新核对 + 触发滚动）、手动开启随机事件、重置某玩家彩蛋进度。

**为什么不做"游戏内 JSON 编辑器"**：这些清单是嵌套结构、条目上百，用游戏内文本框编辑
等于做一个残缺的编辑器 —— 既不好用（没有语法提示、改坏难定位），又容易在误操作后把大块配置写坏。
**热重载 + 文件路径 + 导出/导入** 是同样满足 §9"可编辑 + 全部热重载"但更安全的形态。

## D-29　界面与同步的实现取舍（§3"增量同步"、§8"滚动分页"、§11）

| 项 | 文档措辞 | 实际实现与理由 |
|---|---|---|
| 滚动分页 | "支持滚动分页" | 用**分页 + 每行一个按钮**：自由滚动需要自己换算可见区间与控件坐标，极易出现"按钮跑到屏幕外"；分页把可见行数固定，控件坐标确定。§8 的"滚动分页"由分页满足 |
| 增量同步 | "配置下发需支持增量同步" | **五通道 + 脏标记 + 内容比较 + 修订号**：内容没变就不发包；另对"已打开界面的玩家"每 2 秒做一次兜底标脏（漏了埋点最多 2 秒后自愈） |
| 超大 payload 分片 | "对超大 payload 分片" | `SyncFragment`：16 KB/片、最多 64 片、按 `通道 + 修订号` 重组，旧修订分片与超限包**直接丢弃并记日志**（§14） |
| 非法/超限包 | "直接丢弃并记日志" | 所有上行包先过 `C2SGuard`：动作名必须能解析（否则丢弃）、参数长度上限、每秒 30 包 + 同动作 150 ms 间隔；管理动作还要再查 OP |
| 分支弹窗时机 | §8"10 级触发" | 服务端在快照里给 `branchPrompt`（等级已到且未选分支），客户端**每个会话弹一次**；玩家关掉后不再打扰，可随时在主界面点「选择分支」 |
| 界面暂停游戏 | 未规定 | `shouldPause()` 返回 **false**：战令界面是查阅型界面，暂停会让玩家以为卡住（分支弹窗同理） |

## D-30　披风衣柜的收尾取舍（§9"管理员 GUI 内披风配置页"、§12 目录结构）

| 项 | 文档措辞 | 实际实现与理由 |
|---|---|---|
| 管理员 GUI 内配置披风 | "管理员 GUI 内增加披风配置页面" | **没有新开一个披风页签**，而是复用面板已有的**通用 JSON 配置文件编辑器**：把 `capes.json` 补进 `ServerAdminActions.configFiles()` 白名单（连同修好以前"`titles.json` 能列出来但保存被白名单拒"的错配），并在「称号 / 彩蛋」页加一段只读披风清单（件数 + 每条 `id（名称）贴图=xxx/缺失`）与一个"打开披风贴图目录"按钮。理由：`AdminPanelScreen.SECTION_KEYS` 的下标与 `buildLines()` 的 `switch (section)` 历史上就有错位，为了加一个页签去动页签索引，风险远大于收益；而"改名 / 改解锁条件"本来就是 JSON 编辑，"贴图"本来就是往目录里丢文件——两者都不需要专门的表单控件。**贴图文件本身仍然必须通过文件系统放入**，GUI 里做不了上传（§2 明确禁止玩家上传图片，管理员也不放开二进制上传，否则要引入网络传输与落盘校验） |
| 贴图热重载的粒度 | "热重载" | `CapeManager.reloadIfChanged()` 原来只监听 `capes.json`，**目录里的 PNG 改了不生效**（只有重启或改配置才重读）。现改为"配置没变也照样重读全部 PNG"，但只有字节真的变了才递增 `textureVersion` 并触发全服重发——避免每秒给每个在线玩家重发一遍贴图。判定先比 `[mtime, 长度]` 再兜底 `Arrays.equals`，因为脚本"同一秒内覆盖同名文件"时 mtime 可能不变 |

| 删除贴图 | 未规定 | **不做"移除下发"**：管理员删掉 PNG 后，已经收到过该贴图的客户端仍持有旧纹理（要新增一个"清空披风贴图"的协议包才行）。影响仅限"管理员删图"这一种运维动作，记为此处已知限制 |
| 内置披风贴图怎么来 | 文档只要求管理员放 64×32 PNG | 仓库里**从来没有**这两张图（`haojing_pioneer.png` / `haojing_nightwatch.png`），也没有美术资源。补 `tools/gen_capes.py` 用纯标准库（`zlib`/`struct`/`binascii`，不需要 Pillow）程序化生成两件披风的 64×32 贴图：标准皮肤布局的披风区域、深红褐/夜蓝底 + 金色菱形徽记 + 龙鳞纹 + 包边。理由：仓库要能自洽交付，不依赖外部图片；管理员想换成自己的图，只要文件名与 `capes.json` 的 `textureFile` 一致即可覆盖。**该脚本尚未在任何机器上执行过**（写它的会话无法执行进程） |
| 编译与真机验证 | 不适用 | 上面这批披风改动（`CapeManager` / `ModNetworking` / `HaoJingBattlePassServer` / `ServerAdminActions` / `SnapshotFactory` / `AdminPanelScreen` / 语言文件）是在**完全没有命令执行能力**的会话里写的——该会话的 `pwsh` 被 PowerShell ExecutionPolicy 拦死。因此**只保证语法与逻辑自洽，未经编译**；`tools/gen_capes.py` 同样未执行。接手后必须先 `gradlew.bat build --no-daemon`，再按《进度交接》§6 做真机验证。这不算需求偏差，但属于交接必须知道的事实 |

## D-31　怪物潮刷怪的亮度闸与选点规则（§10 未规定刷怪位置约束）

**文档要求**：§10 只规定事件类型、概率、间隔、时长、参与判定与奖励表，**没有规定怪物在玩家身边的什么位置生成**。

**实际实现（2026-10 玩家反馈后修复）**：旧 `RandomEventEffects.applySpawn` 直接在玩家脚下 ±8 格随机偏移刷怪，**不看亮度、不找地面**——白天露天、火把/灯照亮的基地与生电机房都会刷出怪物，导致机器被破坏。修复后所有 `SPAWN` 效果统一走亮度闸 + 合法地面选点：

| 项 | 默认值（events.json 可调，热重载） | 规则 |
|---|---|---|
| `spawnMaxLightLevel` | 7（0~15） | 候选位置亮度 **≤ 阈值**才允许刷怪；口径与原版敌对怪夜间一致。亮于阈值的位置直接跳过 |
| `spawnRadius` | 8（1~32 格） | 以玩家为中心的水平半径；离玩家水平两格以内的候选列直接换点，避免卡在身上 |
| `spawnMaxAttempts` | 12（1~32） | 每只怪物最多尝试这么多个候选列；**找不到合法暗点就放弃这一只，绝不强制刷到亮处**（日志记录跳过数量） |
| `spawnVerticalRange` | 10（1~32 格） | 候选位置与玩家的垂直高差上限，避免刷到头顶屋顶或脚下洞穴深处 |

**选点校验**：候选列在垂直窗口内自上而下找第一处"脚下实心方块 + 脚位空气 + 头顶空气"，再复核亮度；三项任一不满足就换下一个候选列。

**两个刻意取舍**：
1. **亮度闸对所有 `SPAWN` 效果统一生效**，不区分敌对/友好实体。若管理员要做"白天放宠物"之类的友好实体事件，把 `spawnMaxLightLevel` 调到 15 即可关闭亮度闸。
2. **亮度取世界综合亮度**（方块光 + 天空光），与原版怪物生成判定同源；不单独区分光照类型，避免两套口径在地下/室内互相打架。

## D-32　随机事件自查修复与新增默认事件（2026-10-22 全自主决策）

**触发**：用户要求"自查 bug，随机事件自行新增内容，全部自主决策"。通读事件四层代码（配置/调度/效果/定义）后，修复 4 处问题、新增 4 个默认事件。

**修复**：

| 问题 | 根因 | 修法 |
|---|---|---|
| 权重溢出可致事件系统崩溃 | `pickWeighted` 用 `int total` 累加权重；配置校验只夹下限不夹上限，两条 2^31 级权重相加溢出为负，`random.nextInt(负数)` 抛异常 | `validate()` 把权重夹紧到 1~100 并 WARN；`pickWeighted` 改用 `long` 累计 + `random.nextLong(total)`（双保险，不依赖校验） |

| 同一物品可能重复发放 | 同一事件"奖励表 ITEM"与"效果表 ITEM"并存时玩家各拿一份，配置层无提示 | `validate()` 检测并存并 WARN（不拦截，保留"有意双份"的活动空间） |
| `RandomEventEffects` 死参数 | `applyStart/applySpawn` 的 `List<UUID> online` 从未使用（实际遍历全服在线玩家），误导读者 | 删除死参数并注释说明"事件是全服事件，与参与判定无关" |

**新增 4 个默认事件**（`default_events.json`，公告文案进客户端 `zh_cn.json`，类型枚举各新增一项）：

| id | 类型 | 参与判定 | 效果 | 奖励 |
|---|---|---|---|---|
| `ev_pillager_raid` | PILLAGER_RAID（掠夺者入侵） | KILL_ENTITY ×2 | 刷掠夺者×3 + 卫道士×1（走亮度闸） | 经验 90 + 京币 8 + 绿宝石×4 |

## D-34　自然月周期与到期自动轮换（2026-10-22 用户拍板：每月 1 号一个赛季、系统自动滚动）

**触发**：用户明确"下一个赛季在 11 月 1 日开启，以后每一个月，一个赛季"。交互问答中拍板两个口径：
① **系统自动滚动**（到期自动归档上赛季、重置等级/任务/分支、全服公告，无需管理员手动改 `seasonId`）；
② **自然月**（每月 1 号 0 点切换，赛季长度跟随日历 28/30/31 天，而非固定 30 天）。

**对 D-33 取舍 1 的翻转与保留**：
- 翻转：D-33 当时决定"不做自动改 seasonId"，理由是系统猜不出赛季命名。本轮用户显式开启自动轮换后，
  系统按 `S1 → S2 → S3` 规则自动递增赛季 ID，归档/重置/公告复用既有 `checkAndRoll` 链路。
- 保留：自动轮换**只清档与轮换赛季 ID**，任务池、奖励表、主题名（`themeName`）仍由管理员手动更换 ——
  这些玩法内容系统同样猜不出，也不应隐式换库。

**新增内容**：

| 项 | 内容 | 默认 |
|---|---|---|
| `cycleMode`（`season.json`） | `"natural"` 自然月（开始日所在月份下月初到期）/ `"fixed"` 固定时长（`start + durationDays` 天，兼容旧配置与既有行为）；非法取值校验时归一化为 `fixed` 并 WARN | `fixed`（旧配置 Gson 缺字段落到默认值，行为不变） |
| `autoRollover`（`season.json`） | 到期是否由系统自动归档并开启新赛季；关闭时只做倒计时与提醒，沿用 D-33 手动推进口径 | `false`（清档不可逆，必须显式开启） |
| `SeasonSchedule.isRolloverTime` | 到期日当天（剩余 ≤ 0）即到达轮换时点；与提醒口径 `isDue`（超期 < 0）分开，避免提醒语义被轮换时点改动 | — |
| `SeasonResetService.checkAndAutoRollover` | 维护循环在 `checkAndRoll` 之前调用：开关开启、配置了开始日、到达轮换时点、归档线程空闲才执行；先改内存赛季 ID/开始日，`saveAndReport()` 确认落盘成功才继续，**失败回滚内存原值并中止本轮**（防止配置没写进磁盘却清了档，重启后二次归档）；成功后复用 `checkAndRoll` 完成在线主线程重置、离线后台归档、待播公告与 `markSeasonRolled` | — |
| `nextSeasonId`（纯函数） | `S1/s3/S10` 等 `S+数字` 大小写不敏感递增；非匹配格式追加 `-yyyy-MM` 月份后缀，避免不同赛季共用 ID 导致归档 `season_<id>.json` 互相覆盖；空 ID 兜底 `S2` | — |
| 新赛季开始日推算 | 自然月：补回本月 1 号（宕机几天后开机也不截短当月）；固定时长：沿旧开始日向后推 `durationDays` 天，保持节奏连续 | — |
| 管理面板 | `Admin` 快照补 `autoRollover`/`cycleMode`，概览新增一行轮换状态（开启时标注周期模式，关闭时提示手动推进）；到期文案按开关区分 | — |
| 内置模板 `default_season.json` | 新部署落地 `natural` + `autoRollover=true` + `seasonStartDate="2026-11-01"`；线上已有 `season.json` 不被模板覆盖，上线前需管理员核对三项字段（见管理员手册 §4.3） | — |

**取舍说明**：
1. **配置落盘成功才清档**：赛季滚动不可逆，`saveAndReport()` 返回 boolean 供调用方判定；普通 GUI 保存
   仍走 `save()`（写失败只记日志、内存配置继续生效），两套语义分开。
2. **到期日当天即轮换**：自然月要求每月 1 号切换，因此轮换时点取 `days <= 0`；`isDue`（days < 0）
   仍服务于"已超期"提醒文案，两个口径不合并。
3. **测试夹具回到历史口径**：`ServerTestEnv` 加载模板后强制 `cycleMode=fixed`、`autoRollover=false`、
   `seasonStartDate=""`，避免新模板默认值污染 D-33 的固定时长提醒用例；新用例各自体内显式开启。

## D-40　头顶称号 Mixin 按 1.21.11 新渲染管线对齐 `renderLabelIfPresent` 签名（2026-10-22 真机崩溃修复）

| 项 | 实现 | 理由 |

| 签名核对 | 以工程锁定的 Yarn `1.21.11+build.6` mappings 为第一依据，再从 Loom `minecraft-merged.jar` 反编译 `EntityRenderer` 与 `EntityRenderState` 字节码逐项确认方法描述符、参数类型与名称字段，不凭旧版本记忆或经验名猜测 | 崩溃报告只给 intermediary 描述符，必须落到本机锁定 mappings 与字节码上核对；防止按错误的 Yarn 名二次改崩 |
