# 打包与部署

> 面向"要把这个 Mod 跑起来"的人（包括未来的你）。需求文档 §15 要求的「编译打包教程 + 部署说明」就是本文。

---

## 1. 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| JDK | **21** | 需求文档 §1 锁定 JDK 21；本机实测 `21.0.12.1` |
| Gradle | 用工程自带的 wrapper（**9.2.0**） | 不要用系统 Gradle，版本不一致会触发 Loom 行为差异 |
| 网络 | 能访问腾讯镜像 + BMCLAPI | 本机 hosts 屏蔽了 `*.mojang.com` 与 `github.com`，工程已配置好镜像绕法（见 `gradle.properties`） |
| 磁盘 | 约 3 GB 空闲 | Loom 缓存（Minecraft 客户端/服务端 jar + 反编译源码）体积不小 |

**版本锁定**（唯一来源是 `gradle.properties`，不要在各处硬编码）：
MC `1.21.11` / Fabric Loader `0.18.1` / Fabric API `0.140.2+1.21.11` / Loom `1.14.6` / Yarn `1.21.11+build.6`。

## 2. 打包（两步，必须在 ASCII 路径下执行）

工程目录名含中文（`战令ds`），而 Gradle 的测试 worker 用 Java `@argfile` 传类路径、
JDK 用系统 ANSI 代码页（GBK）解析它，**处理不了非 ASCII 路径**。因此：

```bat
:: 1) 建一个 ASCII 联接（只需一次）
mklink /J C:\Users\<你>\Desktop\haojing-bp "C:\Users\<你>\Desktop\战令ds"

:: 2) 从 ASCII 路径进入，并把 GRADLE_USER_HOME 也用 ASCII 路径引用
cd C:\Users\<你>\Desktop\haojing-bp
set GRADLE_USER_HOME=C:\Users\<你>\Desktop\haojing-bp\.gradle-home
gradlew.bat -g %GRADLE_USER_HOME% build
```

**`GRADLE_USER_HOME` 也必须走 ASCII 路径**（同一条 JDK 限制）：直接写中文目录会让
**所有单元测试**报 `ClassNotFoundException: GradleWorkerMain`。这一点在第 7 阶段实测过，
是目前唯一会让人以为"测试全挂了"的坑。

产物：

```
server/build/libs/haojing-battlepass-server-0.1.0-SNAPSHOT.jar
client/build/libs/haojing-battlepass-client-0.1.0-SNAPSHOT.jar
```

> **在 DSH 沙箱里打包**：`:server:remapJar` 需要真正写回 jar，而沙箱会让 `Files.isWritable()`
> 对**所有路径**恒为 false（zipfs 判为只读），因此打包会报 `the jar file ... can't be written`。
> 编译与测试不受影响。普通终端不受影响；在沙箱里需要一次性提权。
> 另外沙箱下 Gradle 的 `File watcher` 原生线程会打 `error = 5` 的 stderr 噪音，
> 判断成功与否要看 `BUILD SUCCESSFUL` 而不是退出码。

**验证**：`gradlew.bat -g %GRADLE_USER_HOME% test` → 应显示 **288 个测试全通过**。

## 3. 部署到服务端

1. 安装 **Fabric Loader 0.18.1**（服务端安装器选 `1.21.11`）。
2. 把 **Fabric API `0.140.2+1.21.11`** 放进 `mods/`。**这是硬依赖**（事件、数据包、命令注册都用到）。
3. 把 **`haojing-battlepass-server-...jar`** 放进 `mods/`。
4. 启动一次服务端，会自动生成：

```
config/haojing_battlepass/     season.json / daily_tasks.json / rewards.json / shop.json
                              eggs.json / codes.json / events.json / milestones.json
data/haojing_battlepass/       players/<uuid>.json   global/<uuid>.json   state.json
data/history/                  season_<id>.json（赛季归档）
```

5. 需要跨服/代理时看第 6 节。

**服务端不需要客户端 jar**；客户端 jar 只装在玩家游戏里。

## 4. 部署到客户端

1. 玩家用 Fabric Loader 启动 1.21.11（同样需要 Fabric API）。
2. 把 **`haojing-battlepass-client-...jar`** 放进客户端 `mods/`。
3. **打开界面有两种方式**：
   - 按 **`B`** 键（默认快捷键，可在「选项 → 控制 → 按键绑定 → 镐京方块协会战令」里改）；
   - 输入指令 **`/battlepass`**。
   OP 用 **`/battlepass admin`** 打开管理面板（管理面板没有快捷键，避免误触）。

> **没有装客户端 Mod 的玩家会被拒绝进入**（§2）：这是本模组的显式设计，
> 只用于避免玩家进服后看到空白界面。它**不是反作弊** —— 改过客户端的人可以绕过，
> 所有判定仍然只在服务端。本地测试时把 `season.json` 的 `devMode` 设为 `true` 即可放行原版客户端。

## 5. 升级流程

1. **先备份**：管理员面板点「导出配置」（或手动复制 `config/haojing_battlepass/` 与 `data/`）。
2. **看协议版本**：`ModConstants.PROTOCOL_VERSION` 变了就必须**同时更新服务端与所有客户端**，
   否则版本不匹配的客户端会在配置阶段被明确拒绝（而不是进服后数据错乱）。
3. 替换 jar → 重启服务端 → 观察日志前缀 `[HaoJingBP]` 的加载摘要。
4. 存档向后兼容由 `schemaVersion` 字段保证；旧存档缺失的新字段会按默认值补齐（代码里逐处兜底）。

## 6. 代理（Velocity / BungeeCord）注意事项

握手发生在**后端服**与玩家之间。代理不懂自定义 payload，正常会原样转发，但要注意：

| 项 | 说明 |
|---|---|
| 现代转发 | 代理必须开启 Velocity modern forwarding（或 BungeeCord 的 `online-mode=false` + `ip_forward`），否则配置阶段由代理完成，后端服收不到握手 |
| 未知 payload | 少数安全插件会丢弃它不认识的 payload。需要把命名空间 `haojing_battlepass` 放行 |
| 跨服跳转 | 后端之间切换会重新走一次配置阶段，因此会重新握手 —— 这是**正确行为**，无需处理 |
| 拒绝信息 | 玩家看到的踢出提示来自客户端 `zh_cn.json`（`haojing_battlepass.net.kick.*`），代理上的玩家同样能看到 |

## 7. 备份与恢复

- **一键导出**：管理面板「导出配置」→ 写到 `data/haojing_battlepass/backup/<时间戳>/`，
  含 8 份配置 + `state.json`（里程碑计数与刷新标记）。
- **一键导入**：在「取值」框里填备份目录名（**只允许目录名**，不能带 `/` 或 `..`）→ 点「导入配置」→ 自动全量热重载。
- **玩家数据**：`data/haojing_battlepass/players/`（赛季）与 `global/`（永久：星币/称号/收藏册）。
  每个 JSON 写入时都会留一份 `.bak`；文件损坏时启动会自动回滚并记 ERROR（§12、§14）。
- **赛季归档**：`data/history/season_<id>.json` 永不删除，收藏册的历史档案来自这里。

## 8. 停止与重启

需求文档 §2 明确**不写任何停机/重启代码** —— 服务器定时重启由外部脚本负责。
本模组在 `SERVER_STOPPING` 时会：停刷新线程 → 停赛季归档线程 → 落盘里程碑计数 → 同步落盘全部玩家数据。

**不要在运行中直接 `kill -9`**：那会丢掉最近 5 秒（玩家数据）到 60 秒（里程碑计数）的改动。
正常 `stop` 不会丢任何数据。

## 9. 首次启动冒烟清单（照这个顺序看日志）

### 服务端（`logs/latest.log`，全部带 `[HaoJingBP]` 前缀）

1. `服务端模组骨架已加载（阶段 2-6：…）` —— 入口点被正确加载。
2. `模块已就绪：赛季=S1 长夜=true(00:00~06:00 倍率 0.5) 任务池=42 等级奖励=N 级 商店=7 件`
3. `阶段 6 已就绪：彩蛋=13（全局 6 / 长夜 4 / 赛季限定 1）随机事件=5 种 口令=3 条 里程碑=10 条`
4. `网络层已注册（客户端校验=开启 通过 0 次 / 拒绝 0 次 服务端协议=1）`
5. `数据目录：config=… players=… global=… history=…`（确认落在你期望的目录）
6. 玩家进服时：`客户端校验通过：Mod 版本 … 协议 1`

### 客户端（`logs/latest.log`）

1. `客户端网络层已注册`
2. `客户端模组已加载（阶段 7：握手 + 双向包 + 中文界面）`
3. 连接服务器时：`已向服务端发送握手（协议版本 1）` → `服务端校验通过（服务端协议 1）`

### 常见启动失败的对照表

| 日志里的关键字 | 原因 | 处理 |
|---|---|---|
| `EntrypointException` / `does not implement ModInitializer` | 入口点类型放错（`main` ↔ `client`） | 客户端必须在 `entrypoints.client`，服务端在 `entrypoints.main` |
| `IllegalArgumentException: Packet type … is already registered` | 同一批 payload 被注册两次（单机同时装两个 jar 时最容易出现） | 已由 `common/net/ModPayloadRegistration` 一次性注册器解决；若仍出现，说明有别的模组占用同名通道 |
| `Mixin apply failed` / `InvalidInjectionException` | Mixin 注入点与目标版本不匹配 | 本工程三处注入点已与 1.21.11 逐项核对（见《进度交接》第 7 节） |
| `缺失依赖 fabric-api` | `mods/` 里没有 Fabric API | 放 `fabric-api-0.140.2+1.21.11.jar` |
| 客户端界面一直"正在等待服务端数据…" | 包通道没通（服务端没发或客户端没注册） | 看服务端日志有没有 `已同步通道`（需把日志级别调到 DEBUG）；确认两端协议版本一致 |
| 玩家被踢，提示需要客户端 Mod | 正常行为（§2）；确认玩家装的是**客户端** jar | 本地测试可临时把 `season.json` 的 `devMode` 设为 `true` |

> **单机（集成服务端）注意事项**：单人游戏时客户端与服务端两个 jar 会**同时加载**，
> 因此两端的初始化都会跑到。本模组已针对这种情况做了保护（payload 一次性注册、
> 服务端模块只在 `SERVER_STARTING` 时初始化）。这也是为什么两个 jar 都必须装。
